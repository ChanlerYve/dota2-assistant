## 2. 开发时间线（按提交）

### ① 评审现状，产出体检报告

先通读既有实现并逐条实测，产出了独立的评审报告（见根目录
[dota2-assistant-review.md](../dota2-assistant-review.md)）。核心结论：

- 架构、合规边界、可解释性设计是**对的**，工程质量扎实（当时 37 项测试全绿）；
- 但存在 **8 个实测确认的缺陷**（编号 D1~D8）与一个结构性缺口（无法自动感知 BP）；
- **「读屏幕识别 BP」这条路技术上不通、合规上有明确风险**——这是报告里最重要的结论。

### ② 语音录入 + 别名扩充 + 修复 8 个缺陷

- **语音**：Windows 自带 `System.Speech`，把识别范围**约束成英雄名语法**（全名 + 别名），
  离线、零依赖。识别文本走**与手打完全相同**的解析管线，所以合规边界不变。
- **别名**：新建 `data/aliases.json`（530 条），解析器改为打分匹配 + 出场率消歧。
  修掉了 `ls` 被错解析成 Vengeful Spirit 的真 bug。
- **D1~D8 全部修复**，详见 §3。

### ③ 容器化 + 智能体部署契约

- `Dockerfile` / `docker-compose.yml` / `.dockerignore` / `.env.example`。
- 服务层改造：`/api/health` 探针、Bearer token 鉴权、`D2A_*` 环境变量、配置持久化。
- `docs/agent-deploy.md`：为**自动化执行**写的部署契约（预检 → 模式决策 → 命令 →
  验证闸门 → 失败处置表 → 硬约束）。

### ④ 版本突出性分析（统计口径）

用户需求是「从数值层面分析当前版本各英雄是否存在非常突出的情况」。
检索后找到学术先例（[Kinetik 2022](https://kinetik.umm.ac.id/index.php/kinetik/article/view/2698)
用 `μ + kσ` 阈值法做英雄强弱判定），但做了四处加强。详见 §4.1。

### ⑤ 把版本结论接进选人引擎

分析结果作为**决胜级微调**影响推荐（封顶 +2 分），而不是替代原有因子。详见 §4.2。

### ⑥ 真实协同数据补全

「配合」因子此前只覆盖 35 个英雄，随机两英雄约 72% 查不到数据。
改用 OpenDota **Explorer SQL** 从 247 万条 pick 记录算协同 + James–Stein 收缩。
覆盖 35 → 126 个英雄。详见 §4.3。

### ⑦ BP 阶段化权重

「第一手选什么」和「最后一手选什么」是两个不同的问题，此前却用同一套权重。
改为按阶段对权重做乘性调制。详见 §4.4。

## 3. 修复的缺陷清单

### 3.1 评审报告确认的 8 项（D1~D8）

| 编号 | 问题 | 修法 | 验证 |
|---|---|---|---|
| D1 | 对位矩阵被 `top_k=14` **按显著性截断**，偏袒热门英雄 | 取消截断 | 1015 → 4856 条边 |
| D2 | 空 BP 时 `team_fit` 返回常数 → **第一手推荐不含位置信息** | 空阵容时直接返回位置适配 | Axe@3 70.6 vs Axe@5 44.1 |

| D4 | 协同因子无数据时返回常数，白白消耗权重 | 权重重归一化让给其他因子 | 不再白送 10% 权重 |
| D5 | `min_games` 是**死参数**；「没玩过」惩罚只在有队友时生效 | 两条分支都生效 | `min_games=50` 正确过滤 |
| D6 | 版本号恒为占位符 `"current"` | 从 `constants/patch` 取真实版本 | patch=7.41 |
| D7 | 敌方位置推断用**硬编码顺序** | 全局最佳优先分配 | 6/6 达到理论上界 |
| D8 | 不按位置过滤；`Candidate.position` 语义误导 | 显式惩罚 + `position_legal` | Axe@5 57.8 → 44.1 |

### 3.2 顺带发现并修掉的既有代码缺陷

这些不在评审报告里，是实现过程中撞出来的：

| 问题 | 后果 | 说明 |
|---|---|---|
| `python -m d2a --cli` **完全不可用** | 入口把 `--cli` 转发给 CLI 的 argparse，直接报错退出 | 以前一直用 `--web`/`--demo` 路径，所以没暴露 |
| 管道输入带 BOM | 第一条命令变成 `\ufeffpool`，报「未知命令」 | 从文件/管道喂输入时必现 |
| `pool_from_stats` **清空**简写英雄池 | 与自身注释「覆盖同名」不符 | 被自己写的测试抓到 |
| `DEFAULT_TUNING` 是**共享可变单例** | 一个实例改 `tuning`（含 `set_bracket`）会**泄漏到所有实例** | 多实例场景（Web + CLI）互相干扰；潜伏已久 |
| `--min-position-games` 声明但从未使用 | 死参数 | 与其写进文档，不如删掉 |

### 3.3 我在本会话中自己引入、又被测试抓出的问题

诚实记录——这些说明「测试是写给人看的，不是走过场」：

| 我写错的东西 | 症状 | 教训 |
|---|---|---|
| `pool_mad` 用**收缩后**的胜率计算 | 收缩把均衡英雄拉到同一先验值 → MAD=0 → 兜底把所有人压到同一把尺子。**三个胜率差 8pp 的档位算出完全相同的 z（6.957）** | 稳健统计量的输入必须是原始观测，不能是处理后的值 |
| 趋势判断用 **z 的斜率** | `z = excess/MAD` 尺度不变 → 池形状相同则 z 恒定 → 斜率恒为 0 | 已把「z 尺度不变」这个事实本身写成测试 |
| 容器挂载卷**遮住**镜像里的数据 | `./data-docker:/app/data` 会盖掉 `COPY data/`，新卷首启找不到 heroes.json | 镜像另存基线 `/opt/d2a-baseline`，入口按「只补不覆盖」播种 |
| POST **先响应后落盘** | 客户端可能拿到 200 时文件还没写完，「改完立刻读配置」读到旧值 | 改为先执行 → 再落盘 → 最后写 socket |
| 测试里把 Medusa 的**猎物当克星** | `matchups[X][Y]` 是「X 面对 Y 的优势」，正值表示 X 占优 | 找克星要到**对方自己的行**里找 |
| 合成数据的配对**取值全同** | 估不出信号方差 → 全被收缩到 0 → 测试失败 | 那不是 bug 而是「看不出信号就不给意见」的正确保守行为 |

## 4. 四项核心能力的口径与取舍

### 4.1 版本突出性分析

**不能按胜率排序**：Dota 每场必有且只有一个胜者，所有英雄胜率在数学上**被迫**
围绕 50%，所以「胜率 52%」本身不构成证据，要看它在英雄池里**偏了几个离散单位**。

判定「突出」要同时过三道闸门：

1. **效应量** ≥1.5pp（样本动辄几十万，0.1pp 也能"显著"但无意义）；
2. **Wilson 区间完全落在池中位数同侧**；
3. **BH-FDR 5% 校正**（一次比 127 个，不校正平均 6 个是纯运气）。

两个刻意的统计选择：
- 用 **MAD** 而非标准差度量离散度——标准差会被极端英雄抬高，让极端英雄**自己显得不显著**；
- **不用朴素两比例 z 检验**——基准是从同一批数据估出来的，当常数用会高估显著性。

**数据自洽性校验**：按出场加权的总胜率必然 = 50%（实测 0.5000），偏离即数据有缺。

实测（patch 7.41，3991 万场）：显著偏强 34 个 / 偏弱 33 个。

### 4.2 版本结论如何影响推荐

作为**决胜级微调**（封顶 +2 分），不是替代因子。语义是「两个候选在你手里差不多时，
优先拿本版本数据异常的强点」，而不是「版本强就能无视你会不会玩」。
**显著偏弱只提示、不扣分**（很多英雄是「版本弱但克制特定阵容」）。

加分写进 `contribution.version_outlier`，所以**可对账**。

### 4.3 协同数据

```
synergy(A,B) = WR(A、B 同队) − (WR_A + WR_B) / 2
```

三个必须说清的取舍：
1. **不设时间窗**——Explorer 的 `matches` 近期窗口极小（近 30 天仅 414 场），
   按窗切凑不出样本。协同比胜率更跨版本稳定，代价是混合多版本。
2. **必须收缩**——单配对样本中位数 609 场，二项噪声 SD ≈1.4% vs 真实信号 ≈1.7%，
   信噪比仅 1.26。用 James–Stein `n·s²/(n·s²+0.25)`，`s²` **从数据估**。
3. **`|协同| < 0.002` 丢弃**——低于噪声量级，留着只是让因子「看起来有数据」。

**已知偏差**：会混入「选秀情境」（某英雄常被抓在优势阵容里，则与谁搭都偏高）。
要分离「组合本身的价值」需要在比赛层面控制阵容质量，超出当前范围。

### 4.4 BP 阶段化权重

按**敌方已亮人数**分阶段（0~1 早手 / 2~3 中盘 / ≥4 末手），对权重做**乘性调制**：

| 因子 | 早手 | 中盘 | 末手 |
|---|---|---|---|
| 对位 | ×0.55 | ×1.00 | ×1.70 |
| 版本 | ×1.30 | ×1.00 | ×0.80 |

是调制不是替换——用户偏好仍然保留；中盘刻意接近中性，即「大部分时候按你设定的来」。

## 5. 明确的「不做」及其依据

**不做读屏 / 不自动感知 BP**，依据（详见 [评审报告](../dota2-assistant-review.md) §2）：

1. GSI 的 `draft` 字段**在天梯 All Pick 下为空**（Valve 官方 issue 确认；
   请求开放的那个 issue 挂了两年未解决）；
2. Overwolf 能读内存是因为**与 Valve 有协议**，普通开发者复现不了；
   而它公开的事件列表里**也没有任何 draft/pick 事件**；
3. Valve 的措辞覆盖「读客户端数据」，并用**蜜罐**主动封禁过 4 万个账号，
   同一次更新还专门堵掉了选人阶段的信息读取；
4. 即便只 OCR 不读内存，也属未获批准的灰色地带，且社区实践者自评「慢且不准」。

**语音在这里只被当作输入法**——把说的话变成文本，再走与键盘相同的解析管线。
不读画面、不感知 BP，合规边界与手打完全一致。

## 7. 验证状态
```
单元测试      229 项全绿
全链路自检    数据 / 引擎 / 版本分析 / Web API / 语音 / 容器 全通过
Docker 静态    37 项校验通过
文档链接      4 个文档失效链接 0、失效锚点 0
```

统计方法的正确性是**对照已知数值**验证的，不是「能跑就行」：

| 检验项 | 对照基准 |
|---|---|
| Wilson 区间 | 教科书值 `50/100 → 0.4038` |
| MAD | 手算 `[1..5] → 1.4826`；且对极端值稳健（标准差被抬高 260×，MAD 不动） |
| BH-FDR | Benjamini–Hochberg 1995 原论文算例（10 个 p 值全拒绝） |
| 数据自洽性 | 加权总胜率 = 0.5000（数学必然） |

**未能验证的部分（诚实标注）**：

1. **容器从未真正 `docker build`** —— 本机 Docker daemon 被沙箱拒绝
   （`open //./dockerDesktopLinuxEngine: Access is denied`）。只做了 37 项静态校验。
   首次真实构建若失败，把 `docker compose logs --tail=100` 贴出来。
2. **语音识别未经真人说话验证** —— 沙箱拿不到麦克风（`E_ACCESSDENIED`）。
   已验证到「协议解析 + 监听管线 + 引擎加载」，识别那段需真机跑
   `python -m d2a --voice-probe`。
3. **赛后同步只用一个公开账号试过** —— 未覆盖「账号未开公开数据」等边界。

## 8. 下一步（含前置条件）

按「价值 / 成本」排序，**每项都标了前置条件**，避免接手时踩空。

### 8.1 立即可做

| 项 | 价值 | 前置 |
|---|---|---|
| **容器真实构建验证** | 高（唯一未验证的交付面） | 一台 Docker daemon 可用的机器 |
| **语音真机验证** | 高（同上） | 有麦克风 + 中文语音包的 Windows |
| **协同数据去偏** | 中高 | 需在比赛层面控制阵容质量（按楼层/是否末选/对局段位分层），Explorer 支持 |
| **队友视角** | 中 | 无需新数据；扩展 `recommend` 到 5 个位置槽 |
| **分位置期望值基准** | 中 | 需解析对局的 GPM/补刀（`matches` 详情已有 `benchmarks` 字段） |

### 8.2 需要外部条件

| 项 | 前置 |
|---|---|
| **顶分局 / 职业切片** | STRATZ token（`stratz.com/api` 用 Steam 登录领）。当前档位切片最高只到 Divine，因为 OpenDota 公开数据里 Immortal(8) 恒为 0 |
| **BP 自动录入** | ⛔ 不做，见 §5 |

### 8.3 值得注意的技术债

1. **`tools/windows-push/` 与本机推送工具**：仓库里有一份 `tools/windows-push/`
   是给受限网络环境用的远程 helper，**不属于功能代码**。如果推送链路换成正
   常网络，这个目录可以删掉。
2. **`data/synergies_live.json`（316KB）**：刷新产物，不入 git；
   但每次刷新会重写，注意别把它误提交。
3. **Explorer 接口不稳定**：实测有 SSL 握手超时。`refresh_synergies.py` 已做
   重试 + 降级分批 + 失败批次补跑，失败时**会明确报告哪些英雄覆盖不完整**。
4. **`.gitattributes` 与 CRLF**：提交时 git 会提示「CRLF will be replaced by LF」，
   属正常（仓库统一 LF）。不要为此改配置。

## 9. 给接手者的三句话

1. **改引擎前先读 `d2a/stats.py` 和 `d2a/outliers.py` 的模块文档**——
   那里的统计取舍（MAD、经验贝叶斯、FDR、为什么不用两比例检验）都有理由，
   不是随手写的常数。
2. **验证要跑 `python tools/selftest.py`，不要只看单测**——它覆盖了数据完整性、
   引擎不变量、Web API、语音管线与容器入口，是唯一一条端到端检查。
3. **先看本文 §3.3**——我在实现过程中犯过的错都在那里。多数是「输入没保持原始」
   或「拿不同场景做对比」这类问题，很容易重犯。
